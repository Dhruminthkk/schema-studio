Install and run

Node 18 or newer. No backend, no account, no network calls at runtime.

# install and start the dev server
npm install
npm run dev        # http://localhost:5310

# static bundle, output in dist/
npm run build
npm run preview

A build writes three pages: the app at dist/index.html, and these two under dist/site/, so the bundle is self-contained and the app can link to its own documentation.

The site/ folder is still plain HTML with no build step of its own — open the files directly, or serve the folder with anything, and they work.

A five-minute tour

The fastest route to understanding what the tool is for.

  • It opens on the start screen. Import your own JSON or SQL DDL at the top, or pick one of the bundled models below it. Pick policy / policy_term field disposition — two tables, 113 fields.
  • You are in Core view — each table shows named field groups rather than every column. Switch to Detail in the toolbar to see the columns.
  • Click policy_term, then the field amount_outstanding. The inspector shows its legacy source, its fill rate, that it is computed rather than stored, and the finding that says why.
  • Open Walkthrough and play Policy vs PolicyTerm. Five steps, each focusing the canvas on the tables it is talking about.
  • Open Rationale for the same schema — the long-form argument, including what combines into what and why.
  • Switch schema from the Import menu to Policyholder: normalised, then denormalised, then minimal. Same catalog, three shapes.
Start here, and getting back

Your choice is remembered, so the next visit opens straight onto that schema instead of asking again. Click Schema Studio in the top-left corner to return to the start screen — the subtitle there is always the schema you are looking at.

The start screen

Nothing is loaded until you choose something.

Bring your own comes first: a JSON schema or a SQL DDL file, read in the browser and never uploaded. Below it are the bundled models — the Ardent Mutual worked example, and three small starter schemas for orientation.

Your choice is remembered in localStorage, so a return visit opens straight onto it. To come back and pick something else, click Schema Studio in the top-left corner — its subtitle always names the schema currently loaded. Once a schema is open, Esc closes the start screen without changing anything.

The canvas

Drag, pan, zoom, and let the layout engine arrange by data class, domain and connection.

Moving around

  • Pan — drag empty canvas, or scroll
  • Zoom — the toolbar buttons, or scroll with a modifier
  • Fit to screen — frames every table in view
  • Drag a table — position is kept in the schema and survives export

Layout

Auto-arrange places tables in three zones by data class — master and reference on the left, variant and config in the middle, transactional and derived on the right — groups each zone by domain, then resolves overlaps. It is deterministic: run it twice and you get the same arrangement, so it is safe to use as a reset.

Density

Core renders each table as its field groups with a count and a marker per group: a dot for a group containing warnings, another for one containing computed fields. Detail renders every field. Core is the right altitude for a review conversation; Detail is for working.

Relationship lines

Straight or orthogonal. Cardinality is drawn from each relationship's type — 1:1, 1:N, N:1, N:M.

The inspector

Click any table or field. The right-hand panel shows everything the schema knows about it.

For a table: its data class, domain, description and purpose, its source of truth and write owner, and the conversation point — the open question this table exists to raise.

For a field: type, keys, nullability, the legacy source it came from, census fill, its category and dashboard role, its sensitivity class, whether it is stored or derived, any formula, and any review findings recorded against it.

Edit mode turns the inspector into a form — rename fields, change types, toggle keys, add and remove tables. Every edit goes through the undo stack.

Degrades quietly

Every enrichment property is optional. A minimal {name, type} field renders fine; supply more and more of the panel lights up.

Search and history

⌘F searches tables and fields together.

Matches highlight on the canvas and in the group rows, so a field buried inside a collapsed group still shows you which table to open. Esc clears.

The History panel lists every change in the session. Undo and redo step through it; the list is the audit trail for a working session, not a saved artifact.

Walkthroughs

A guided tour that pans the canvas through a sequence of focused tables.

Pick one from the Walkthrough menu and step forward. Each step can focus specific tables — everything else dims — and carries a title, a body, the business flows it touches, and any open questions.

Walkthroughs are the difference between handing someone a diagram and walking them through an argument. Author one per model and a stakeholder can follow it without you in the room.

Rationale pages

Long-form design notes, rendered as an overlay beside the model.

A rationale page is a list of typed sections: headings, prose, bullet lists, small reference tables, and coloured callouts. It answers the questions a diagram cannot — why this boundary, what was combined into what, what is still open.

Schema review

A pass over the loaded model that surfaces structural problems.

Findings are grouped by severity and each one jumps to the thing it is about. It catches the errors that are easy to introduce while editing and hard to see on a canvas — a table with no primary key, a foreign key pointing at a field that no longer exists, a table with no relationships at all, a field whose declared type contradicts its own description.

Marking fields for deletion

Record a decision to drop a column, and see what it takes with it.

Tick Marked for deletion on a field and it is stored on the field as drop: true — exported, undoable, and visible to whoever reviews the diff.

Anything whose foreign key points at a marked field becomes orphaned. That state is always derived, never stored, which is the whole point: un-marking the original restores its dependants cleanly, with no stale flags left behind.

A primary key is never dropped

Marking is ignored on a primary key, so you cannot produce a schema that fails to identify its own rows.

Toggle Dropped in the toolbar to show or hide them on the canvas.

Import and export

Four export formats, each aimed at a different reader.

FormatFor
JSONRound-trips losslessly, including positions and every enrichment property. The format to keep.
SQL DDLBuild from. Dropped and orphaned columns are emitted as comments rather than live DDL, so the script runs and the diff still shows what left.
Mermaid (.mmd)Paste into a document or a pull request. Type tokens are sanitised so the parser accepts them.
MarkdownReview in a pull request — a table per entity with descriptions and sources.

Import is offered first on the start screen and first in the toolbar's Import menu. It takes a JSON file shaped { tables, relationships } — including one this tool exported — or a SQL DDL file, which it parses into that shape and reports on anything it could not read. Either way it replaces the loaded schema; it does not merge.

The file is read in the browser. Nothing is uploaded, which is why a real schema is better opened this way than committed to src/data/.

Themes

Eight, not two.

Light: Paper (warm cream), Frost (cool white), Mist (neutral) and Sage (green). Dark: Slate, Midnight, Carbon and Pine.

Domain colours are generated, not listed. Each theme declares a lightness and a chroma; hues are handed out by position in the schema's own sorted domain list, stepping by the golden angle so that however many domains a model has, they stay as far apart on the wheel as they can. A schema from any domain therefore arrives already legible in all eight themes, with nothing to register.

Add your own schema

To explore a schema without committing it, use Import — nothing leaves the browser. To bundle one into the build, three steps and no build configuration.

  • Drop a JSON file shaped { tables, relationships } into src/data/
  • Import it in src/data/schemas.js and append an entry to BUILTIN_SCHEMAS
  • Optionally add a walkthrough in walkthroughs.js and a rationale in rationale.js, both keyed by your schema id
// src/data/schemas.js
import mySchema from './my_schema.json';

export const BUILTIN_SCHEMAS = [
  {
    id: 'my_schema',
    group: 'starter',      // a SCHEMA_GROUPS id — its section on the start screen
    name: 'Acme order domain',
    blurb: 'One line for the start-screen card.',
    description: 'The longer version, shown on hover.',
    data: mySchema,
  },
  // ...
];

Counts come from schemaStats(), so leave them out of the name.

Generate, don't hand-write

A 113-field schema is not something to maintain by hand. Emit the JSON from whatever already knows your model — a catalog query, a profiling job, a migration spreadsheet — and let the walkthrough and rationale counts follow from the generated data rather than being kept in step by hand.

The JSON shape

Two arrays. Everything else is optional enrichment.

{
  "tables": [
    {
      "id": "t_policy",          // unique, referenced by relationships
      "name": "policy",
      "domain": "policy",         // any word you like — drives colour
      "x": 60, "y": 60,           // canvas position
      "dataClass": "master",      // master | reference | variant | config |
                                  // transactional | derived — or your own
      "description": "What it is.",
      "purpose": "What question it answers.",
      "sourceOfTruth": "...",
      "writeOwner": "...",
      "conversationPoint": "The open question this table raises.",
      "fieldGroups": [ { "name": "Identity", "fieldIds": ["f_policy_id"] } ],
      "fields": [ /* see below */ ]
    }
  ],
  "relationships": [
    {
      "id": "r_1",
      "from": { "table": "t_policy",      "field": "f_policy_policy_number" },
      "to":   { "table": "t_policy_term", "field": "f_policy_term_policy_number" },
      "type": "1:N",
      "note": "one policy, one row per term of cover"
    }
  ]
}
Field ids must be unique across the whole schema

Relationships and foreign keys address fields by id, not by table-plus-name. The convention the bundled data uses is f_<table>_<field>.

Field properties

Only name and type are required. Everything else makes the inspector more useful.

PropertyWhat it does
idUnique across the schema. Referenced by relationships, foreign keys and field groups.
name, typeThe two required ones.
pk, unique, indexed, nullableKey and constraint markers, drawn on the canvas and emitted in DDL.
fk{ table, field } — draws the relationship and feeds orphan derivation when the target is marked for deletion.
descriptionFree text. The bundled data packs type, category, census and legacy source into it.
exampleA sample value. Leave empty for anything sensitive — the tool will not mask it for you.
legacyFieldWhere it came from in the source system, e.g. PMAST<43> SI-TOT.
fillPctShare of the population that actually populates it. The single most useful number in a migration.
categoryBusiness concern. Used for grouping when fieldGroups is absent.
sensitivityinternal · confidential · pii · pci. Renders a warning on the field.
dashboardRoledimension · measure · status · detail · excluded.
storagestored · computed · projected · migrated.
computedA formula string. Renders inline with an ƒ marker — "this is not a real column".
warning{ severity, message } — high · medium · low.
issues[{ kind, detail }] — review findings listed in the inspector.
droptrue marks it for deletion. Set by the UI; keep it on round-trip.

Field groups

What Core view renders instead of a column list.

Declare fieldGroups on a table as an ordered array of { name, fieldIds } and the canvas uses it verbatim. Any field you leave out lands in a trailing Other group, so nothing disappears.

Without fieldGroups, fields are auto-classified into business-concern buckets by name. That is a reasonable default for a schema you are exploring, and the wrong answer for one you are presenting — the model that produced the data knows what its own categories are.

A group name starting with . renders as a nested object — the convention the bundled policyholder model uses for embedded sections such as .credit and .compliance.

Writing a walkthrough

{
  "id": "pair-disposition",
  "name": "Policy vs PolicyTerm",
  "description": "What the tour covers.",
  "steps": [
    {
      "id": "intro",
      "title": "One legacy record, two target rows",
      "body": "Prose. A paragraph or two — this is read aloud.",
      "focus": "all",              // or ["t_policy", "t_policy_term"]
      "touches": ["Policy"],        // business flows this step involves
      "questions": ["What is still open here?"]
    }
  ]
}

Register it in walkthroughs.js under your schema id. A schema can have several.

Writing a rationale

A list of typed sections. Six kinds.

{ "kind": "h2",      "text": "Why the split is the hard part" }
{ "kind": "p",       "text": "Prose paragraph." }
{ "kind": "bullets", "label": "Measured, not assumed", "items": ["..."] }
{ "kind": "table",   "head": ["Field", "Count"], "rows": [["...", "..."]] }
{ "kind": "callout", "tone": "warn", "title": "...", "text": "..." }
{ "kind": "spacer" }

Tones are accent, warn and good. Register in rationale.js under your schema id.

The bundled example

Ardent Mutual — a fictional general-insurance carrier on a 1980s MultiValue system.

Every record count, attribute number and fill rate is invented. The shape is what matters, and so are the findings, which are the kinds of thing a real estate produces.

SchemaWhat it demonstrates
policy / policy_term113 live fields, each classified and given a recommendation. The hard question is which columns of a policy*term-keyed file are genuinely policy-level.
Minimal: quote, bind, claimNine tables. A claim attaches to the policy term, not the policy — which term was in force on the date of loss decides what cover applies.
Policyholder ×3One catalog projected three ways: normalised, denormalised, minimal. Same facts, so the shapes cannot drift apart.
blog / ecommerce / saasSmall starter schemas for orientation.
