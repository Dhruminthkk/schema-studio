The problem

A schema diagram tells you the shape. It never tells you what to do about it.

01

Two hundred columns is not reviewable

Dump every field into a box and nobody can see the structure. Grouped by business concern, the same table becomes six things a person can hold in their head.

02

The interesting part is the reasoning

Which columns say the same thing, which are arithmetic over their neighbours, which nobody can name — that is the work. A diagram that only shows boxes hides all of it.

03

Decisions need evidence attached

"Drop this field" is a claim. "Empty in all 604,812 records" is an argument. The second one can be signed off; the first starts a meeting.

Schema Studio carries the evidence with the model — so a review is someone checking an argument, not someone taking your word for it.

Explore

Everything the canvas does

Drag, pan, zoom, auto-arrange by data class, domain and connection. Two density modes: Core shows field groups, Detail shows every column.

Canvas

Navigate a large model without losing the thread

Tables lay out by what they are and what they touch, rather than by the order someone added them: master and reference on the left, transactional and derived on the right, each column grouped by domain. Switch to Core view and a 113-field table becomes five named groups; switch to Detail and every column is back.

  • Drag tables, pan and zoom, fit to screen, auto-arrange
  • Straight or orthogonal relationship lines
  • Full undo and redo with a history panel — ⌘Z ⌘⇧Z
  • Search every table and field with ⌘F

Explain

Walkthroughs and rationale, built in

Author a guided tour that pans the canvas through a sequence of focused tables, with a note at each step and the open questions attached. Pair it with a rationale page that explains why the model is shaped the way it is.

  • Steps focus the canvas on named tables as you advance
  • Each step carries the business flow it supports and its open questions
  • Rationale pages take headings, prose, bullets, tables and callouts
  • Both are plain JSON — generate them from your model, never by hand

Decide

Mark it, review it, export it

Exploring is half of it. The other half is recording what you decided and handing it to whoever builds the thing.

Mark fields for deletion

Tick a field and the canvas shows the blast radius: any foreign key pointing at it becomes orphaned, derived live rather than stored, so un-marking always restores cleanly. A primary key is never silently dropped.

Schema review

A built-in pass over the loaded model surfaces findings by severity — missing keys, dangling references, tables with no relationships, fields that look mis-typed against their own description.

Export in four shapes

JSON to round-trip, SQL DDL to build from, Mermaid to paste into a document, Markdown to review in a pull request. Dropped fields stay in the DDL as comments, so the diff still shows what left.

It opens on a start screen

Nothing loads until you choose it — import your own, or pick one of the eight bundled models. The choice is remembered, so the next visit goes straight back to it. There is no fixed vocabulary either: whatever words your schema uses for domain and data class are taken from the data, labelled and given a colour, so any estate renders without being registered anywhere.

Field properties the inspector understands

Beyond name and type: legacyField, fillPct, category, sensitivity, dashboardRole, storage, computed, warning and issues. Supply them and the tool renders them; leave them out and it degrades quietly.

Bring your own schema

Import is the first thing the start screen offers: a JSON file shaped { tables, relationships }, or SQL DDL it parses for you. Read in the browser and never uploaded, so a real schema needs no commit and no server. To bundle one into the build instead, drop it in src/data/ and register it.

The worked example

Ardent Mutual — a legacy estate with real problems in it

A fictional general-insurance carrier on a 1980s MultiValue system. Every record count and attribute number is invented; the shape is the point, and so are the findings a tool like this exists to surface.

Redundancy

Sums stored beside their own parts

sum_insured_total equals buildings plus contents on every sampled policy. So does the premium tax, the commission amount and the outstanding balance. Each was stored; each can disagree with its own inputs.

Duplication

Two columns, one relationship

agency_code agrees with broker_code on 99.4% of policies across 3,118 distinct values. The 0.6% that differ are the interesting part.

Hidden state

Status written into the search key

The policy file has no status column, so the business writes LAPSED, CANCELLED, VOID, NTU and DECLINED into the alphabetical search key — on 6.81% of policies.

Shape

Parallel arrays that are really rows

Endorsement codes and their texts, rating factors and their values, adjustment dates and their premium deltas — four pairs kept in step by position alone.

Five schemas ship with it: the two-table field disposition, a minimal quote-to-bind-to-claim model, and one policyholder catalog projected three ways — normalised, denormalised and minimal. Plus three small starter schemas for orientation.
